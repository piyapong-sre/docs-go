## ทำไมต้อง generate code

บางงานต้องเขียนโค้ดหน้าตาเดิมซ้ำ ๆ เช่น method `String()` ให้ enum ทุกตัว, mock ของ interface, หรือโค้ดเข้าถึง database จาก SQL ทางเลือกมีสามแบบ

| วิธี | ข้อดี | ข้อเสีย |
| --- | --- | --- |
| เขียนมือ | ตรงไปตรงมา | น่าเบื่อ ลืมอัปเดตง่าย |
| Reflection | ไม่มีไฟล์เพิ่ม | ช้า, พังตอนรันไทม์ (ดู [Reflection](/advanced/reflection/)) |
| **Code generation** | เร็วเท่าโค้ดปกติ, compiler ตรวจได้, อ่าน/debug ได้ | ต้องมีขั้นตอน generate |

ชุมชน Go เลือกแบบที่สามบ่อยมาก เครื่องมือดัง ๆ อย่าง `stringer`, `mockgen`, `sqlc`, `protoc-gen-go`, `oapi-codegen` ล้วนเป็น code generator

## `go generate` ทำงานอย่างไร

`go generate` สแกนไฟล์ `.go` หาบรรทัด comment พิเศษ แล้วรันคำสั่งที่เขียนไว้

```go title="color.go"
package paint

//go:generate go tool stringer -type=Color

type Color int

const (
	Red Color = iota
	Green
	Blue
)
```

```sh
go generate ./...
```

สิ่งที่ต้องรู้

- เขียน `//go:generate` ติดกัน ห้ามมีช่องว่างหลัง `//`
- คำสั่งรันโดยมี working directory เป็นโฟลเดอร์ของไฟล์นั้น
- มีตัวแปรให้ใช้ เช่น `$GOFILE` (ชื่อไฟล์), `$GOPACKAGE` (ชื่อ package), `$GOLINE`
- `go build` และ `go test` **ไม่รัน** `go generate` ให้อัตโนมัติ ต้องรันเอง

### ตัวอย่าง stringer

`stringer` อ่าน const ของชนิด `Color` แล้วสร้างไฟล์ `color_string.go` ที่มี method `func (i Color) String() string` ให้ เมื่อเรียก `fmt.Println(Green)` จะได้ `Green` แทนเลข `1`

ตั้งแต่ Go 1.24 เราเพิ่มเครื่องมือเป็น dependency ของ module ได้ด้วย `tool` directive ทำให้ทุกคนในทีมใช้ version เดียวกัน

```sh
go get -tool golang.org/x/tools/cmd/stringer
```

คำสั่งนี้เพิ่มบรรทัด `tool golang.org/x/tools/cmd/stringer` ลงใน `go.mod` จากนั้นเรียกด้วย `go tool stringer` อย่างใน directive ข้างบน (แบบเก่าที่ยังเจอบ่อยคือ `//go:generate go run golang.org/x/tools/cmd/stringer -type=Color`)

<Aside type="note">
ตัวอย่าง stringer แสดงไว้ให้ดูเฉย ๆ เพราะต้องเพิ่ม dependency `golang.org/x/tools` ตัวอย่างที่รันได้ด้านล่างจะสร้าง generator ขนาดเล็กของเราเองด้วย standard library ล้วน
</Aside>

## ตัวอย่าง: เขียน mini-stringer เอง

generator ทั่วไปมีสามขั้นตอน

<Steps>

1. **อ่าน** source code ด้วย `go/parser` ได้เป็น AST (Abstract Syntax Tree)
2. **วิเคราะห์** AST ด้วย `go/ast` หาข้อมูลที่ต้องการ
3. **สร้าง** โค้ดด้วย `text/template` แล้ว **จัดรูป** ด้วย `go/format`

</Steps>

<Code code={src} lang="go" title="examples/learn/advanced/codegen/main.go" />

```text title="Output"
พบ const ของ Color: [Red Green Blue]

// Code generated by codegen; DO NOT EDIT.

package paint

import "strconv"

func (v Color) String() string {
	switch v {
	case Red:
		return "Red"
	case Green:
		return "Green"
	case Blue:
		return "Blue"
	}
	return "Color(" + strconv.Itoa(int(v)) + ")"
}
```

## อธิบายทีละส่วน

### 1. Parse เป็น AST

```go
fset := token.NewFileSet()
file, err := parser.ParseFile(fset, "color.go", source, parser.ParseComments)
```

- `token.FileSet` เก็บตำแหน่ง (บรรทัด/คอลัมน์) ของทุก node ใช้ตอนรายงาน error
- ถ้า argument ที่สามเป็น `nil` parser จะอ่านไฟล์จาก disk ตามชื่อที่ให้ ในตัวอย่างส่ง string เข้าไปตรง ๆ เพื่อให้รันได้ในไฟล์เดียว
- ผลลัพธ์ `*ast.File` คือต้นไม้ของทั้งไฟล์ `file.Name.Name` คือชื่อ package

### 2. เดิน AST ด้วย `ast.Inspect`

`ast.Inspect` เรียก callback กับทุก node ในต้นไม้ เราสนใจเฉพาะ `*ast.GenDecl` ที่ `Tok == token.CONST` (บล็อก `const (...)`)

แต่ละบรรทัดใน const block คือ `*ast.ValueSpec` จุดที่ต้องระวังคือ iota: บรรทัด `Green` กับ `Blue` **ไม่มี type เขียนไว้** แต่ได้ชนิด `Color` ต่อจากบรรทัดก่อน เราจึงจำชนิดล่าสุดไว้ในตัวแปร `current`

<Aside type="tip">
อยากรู้ว่าโค้ดแบบไหนได้ AST หน้าตาอย่างไร ให้ใช้ `ast.Print(fset, file)` พิมพ์ต้นไม้ทั้งหมดออกมาดู ช่วยได้มากตอนเขียน generator
</Aside>

### 3. Template + `go/format`

`text/template` เหมาะกับการสร้างโค้ดเพราะเห็นหน้าตาผลลัพธ์ชัด `{{range .Names}}` วนสร้าง `case` ทีละตัว ส่วน `{{-` ตัดช่องว่างด้านหน้าออกเพื่อไม่ให้มีบรรทัดว่างเกิน

`format.Source` ทำสองหน้าที่

- จัดรูปแบบให้เหมือนผ่าน `gofmt` ไม่ต้องกังวลเรื่อง indent ใน template
- **ตรวจ syntax** ถ้า template สร้างโค้ดผิด จะได้ error ทันที แทนที่จะไปพังตอน build

### Header `Code generated ... DO NOT EDIT.`

บรรทัดแรกของไฟล์ที่ generate ควรตรงกับ pattern

```text
// Code generated <ชื่อเครื่องมือ>; DO NOT EDIT.
```

เครื่องมืออย่าง `gopls`, linter และ GitHub จะรู้ว่าเป็นไฟล์ generate แล้วเตือนเมื่อมีคนแก้ด้วยมือ หรือข้ามไม่ lint ไฟล์นี้

## ใช้งานจริงในโปรเจกต์

ถ้าจะทำเป็นเครื่องมือจริง ให้ generator อยู่ใน `package main` ของตัวเอง (เช่น `internal/tools/enumgen/`) แล้ว

```go
//go:generate go run ./internal/tools/enumgen -type=Color -output=color_string.go
```

<Aside type="caution">
ให้ **commit ไฟล์ที่ generate แล้ว** ลง git เสมอ คนที่ `go install` หรือ import package ของคุณจะไม่ได้รัน `go generate` และใน CI ให้รัน `go generate ./...` แล้วเช็ก `git diff --exit-code` เพื่อจับกรณีที่ลืม generate ใหม่หลังแก้ source
</Aside>

## แบบฝึกหัด

1. แก้ `source` ในตัวอย่างให้มี `Yellow` เพิ่ม แล้วรันดูว่า generator สร้าง case ใหม่ให้เองหรือไม่
2. เพิ่ม method `func (v Color) Valid() bool` ใน template ที่คืน `true` เฉพาะค่าที่ประกาศไว้
3. ถ้ามี const block ที่ปน type อื่น เช่น `const ( Red Color = iota; MaxSize = 10 )` generator ของเราจะทำงานถูกไหม เพราะอะไร

<details>
<summary>เฉลย</summary>

1. ได้ เพราะ `findConsts` อ่านจาก AST ทุกครั้ง `Yellow` ไม่มี type และไม่มีค่า จึงสืบชนิด `Color` จากบรรทัดก่อน
2. เพิ่มใน template
   ```text
   func (v {{.Type}}) Valid() bool {
   	switch v {
   	case {{range $i, $n := .Names}}{{if $i}}, {{end}}{{$n}}{{end}}:
   		return true
   	}
   	return false
   }
   ```
3. ถูก บรรทัด `MaxSize = 10` ไม่มี type แต่มีค่า (`len(vs.Values) > 0`) จึงตั้ง `current = ""` และไม่ถูกนับเป็น `Color` (ตามกฎของ Go ค่า `MaxSize` เป็น untyped constant ไม่ใช่ `Color`)

</details>
